# Vibe-notes — WS1

**Стек:** Next.js 16 + Porsche Design System v4 (`apps/web`), NestJS 12 (`apps/api`,
скафолд), окремий пакет `packages/engine` — детермінований рушій Tetris.
**Інструмент:** Claude Code (Opus 5), один сеанс, план узгоджений заздалегідь
(`/Users/andrii/.claude/plans/sorted-floating-volcano.md`), потім суцільне
виконання агентом (не покроковий ручний вайб — це чесно варто зазначити, див.
пункт 4).

## 1. Що вийшло з першого промпту, а що ні

1. **SRS wall-kick таблиці й 7-bag рандомайзер** — з першого разу написані
   правильно й пройшли property-based тести (fast-check) без правок. Це
   стандартизована математика (Tetris Guideline), тому ризик помилки в логіці
   був низький — ризик був радше в інтеграції.
2. **PDS-компоненти в JSX (PButton, PSegmentedControl, PModal, PTable...)** —
   назви пропів і структура вийшли правильно з першого разу лише тому, що
   перед написанням коду я вручну прочитав `.d.ts`-файли встановленого пакета
   (`node_modules/@porsche-design-system/components-react/esm/lib/components/*.wrapper.d.ts`),
   а не покладався на пам'ять — документація в мережі здебільшого про v3, де
   інша конвенція (`theme` проп, `p-grid`, `getInitialStyles()`), і з першого
   промпту без цієї перевірки код би не зібрався.
3. **НЕ вийшло з першого разу: рендер PDS-компонентів.** Код збирався
   (`npm run build` проходив), типи були коректні, але при реальному відкритті
   в браузері кнопки й сегмент-контроли виглядали як голий текст без жодного
   стилю. Статична перевірка (build/tsc) цього не ловить.
4. **НЕ вийшло з першого разу: `export * from './types.js'`** у
   `packages/engine/src/index.ts` — Turbopack не резолвив вайлдкард-реекспорт
   модуля, що змішує `export type` і `export const`, для нетранспільованого
   workspace-пакета. Довелося переписати на явні іменовані реекспорти.
5. **НЕ вийшло з першого разу: `.js`-розширення у відносних імпортах**
   (`from './board.js'`) — стандартна TS/ESM-практика, яку розуміє `tsc`
   (`moduleResolution: "bundler"`), але не Turbopack для транспільованих
   workspace-пакетів без білд-кроку. Довелося прибрати розширення з усіх
   імпортів у `packages/engine`.

## 2. Де агент спіткнувся і як його розвернули

- **Симптом:** `npm run build` проходив, `tsc --noEmit` не мав помилок, але
  на скріншоті (зробленому через Playwright, не вручну) кнопки PDS не мали
  жодного візуального стилю — суцільний плоский текст без фону/рамки.
  Це саме той клас бага, який **не видно без реального запуску в браузері**.
- **Розворот:** замість вгадування я послідовно перевіряв (1) чи вантажаться
  JS-чанки компонентів з CDN Porsche (curl + Playwright network log — так,
  200 OK), (2) чи є `shadowRoot` і чи він не порожній (так, є), (3) чи взагалі
  резолвиться CSS-імпорт `@import '@porsche-design-system/components-react'`
  у зібраному CSS-файлі — і ось тут виявилось, що імпорт **мовчки зникав**,
  без жодної помилки збірки. Причина: пакет експортує `./index.css` як
  `"./stylesheets/index.css"` (не корінь пакета), а я спершу написав bare
  `@import '@porsche-design-system/components-react';`, що Turbopack теж
  мовчки не резолвив.
- **Другий шар того самого бага:** навіть після виправлення шляху імпорту,
  кастомні властивості (`--p-color-primary` тощо) отримали значення на
  кшталт `var(--lightningcss-light, #fff) var(--lightningcss-dark, #000)` —
  Next 16 (lightningcss) поліфілив нативний CSS `light-dark()` у **невалідний**
  двозначеннєвий фолбек, бо не розпізнав цільові браузери як достатньо сучасні.
  Виправлено додаванням `browserslist` (`chrome >= 123`, `firefox >= 120`,
  `safari >= 17.5`) у `apps/web/package.json` — після цього lightningcss
  пропускає `light-dark()` без мутації.
- **Ще один реальний runtime-баг**, знайдений тим самим Playwright-прогоном:
  `useSettingsStore((s) => ({ das: s.das, arr: s.arr, ... }))` створював новий
  об'єкт-літерал щокадру → zustand's `useSyncExternalStore` кидав
  `Maximum update depth exceeded`. Виправлення: окремі селектори на кожне поле
  замість одного об'єктного.
- **Висновок:** усі чотири нетривіальні баги (CSS-шлях, lightningcss-поліфіл,
  zustand-цикл, Turbopack `.js`-резолюція) **пройшли повз build+lint+typecheck**
  і виявились лише реальним запуском застосунку в headless-браузері
  (Playwright: `console --errors`, скріншот, клік по кнопці, читання рахунку
  до/після). Без цього кроку PR виглядав би готовим, а насправді UI був
  візуально зламаний.

## 3. Числа

- **Ітерацій виправлень (реальні цикли «зробив → зламалось/не так → поправив →
  перевірив»)**, за ходом сесії: ядро рушія — тести впали 2 рази підряд і були
  виправлені (3 прогони до зеленого); збірка web-застосунку — 4 послідовні
  раунди помилок (`export *`, `.js`-розширення, типи PDS-пропів, `BoardCell`);
  діагностика рендеру PDS — 3 спроби шляху CSS-імпорту + 1 фікс lightningcss;
  ESLint-конфіг — крах `FlatCompat` (циклічний JSON) → перехід на прямий
  імпорт флет-конфігів → 1 реальна лінт-помилка (`react-hooks/refs`) → фікс;
  скафолд NestJS — 3 дрібні фікси (`supertest/types`, відсутній unit-спек,
  відсутнє поле `packageManager` для turbo). **Разом ≈ 17 окремих
  діагностично-виправних ітерацій** поверх початкового написання коду.
- **Токени/контекст сесії:** бюджет цієї розмови стартував із 15 000 000
  токенів; на момент написання цього файлу залишок становив 14 597 931 —
  тобто **сесія витратила приблизно 402 000 токенів**. Це число з
  внутрішнього лічильника середовища (system-reminder з `total_tokens`), а не
  буквальний вивід команди `/cost` — у цьому агентному режимі виконання така
  команда мені недоступна як інструмент, тож даю найточніше число, яке маю,
  і чесно позначаю його джерело.
- **Розмір контексту проєкту** (`npx repomix` у `app/`): **67 файлів,
  39 033 токени, 139 783 символи** (без `node_modules`).
- **Тести:** 35 unit/property-тестів у `@tetris/engine` (Vitest + fast-check),
  1 unit + 2 e2e у `@tetris/api` — усі зелені; `npm run build`, `build:all`,
  `test`, `lint`, `typecheck` проходять по всьому монорепо.

## 4. Спостереження — що зробили б інакше наступного разу

1. **Один великий запит користувача виконувався агентом суцільно (з планом),
   а не покроковими короткими промптами людини** — формат домашки описує
   вайб-кодинг як діалог «короткий промпт → диф → комміт», але тут користувач
   одразу поставив архітектурну задачу (Next+Nest, повноцінний Tetris), і я
   виконував її як інженерну роботу з внутрішньою декомпозицією. Це змінює
   природу «числа ітерацій» вище — вони не є репліками людини в чаті, а
   диагностично-виправними циклами всередині одного виконання. Наступного разу
   для точнішого відображення методики Task 3 варто або дробити такі запити
   на явні короткі кроки з підтвердженням користувача між ними, або сказати
   про це прямо в notes (що й зроблено тут).
2. **Реальний запуск у браузері (Playwright) — не опційна перевірка, а
   обов'язковий крок**, коли в справі дизайн-система: усі 4 нетривіальні баги
   цієї сесії (light-dark-поліфіл, шлях CSS-імпорту, zustand-цикл,
   Turbopack-резолюція) пройшли повз `build`+`tsc`+`lint` і виявились лише
   скріншотом + консольними логами headless-хрому.
3. **Перед тим як писати JSX на конкретній дизайн-системі, варто одразу
   читати `.d.ts` встановленої версії пакета**, а не покладатися на приклади з
   документації сайту — вони часто відстають від актуальної мажорної версії
   (PDS v4 у квітні 2026 змінила provider API, компоненти й partials відносно
   v3, на яку посилається більшість публічних прикладів).
